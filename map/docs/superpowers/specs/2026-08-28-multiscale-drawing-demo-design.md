## 1. 문제 — 한 스케일만 보여주고 끝난다

사용자 관찰: *"가장 최근(좁게)만 작도하는 지표들이 있고 마치 그게 다인 것처럼 끝낸다."*

현재 앱 시연은 지표당 **카메라 구간 하나**를 잡는다(`forge-embed._regionForNode`). 그 구간은 지표의 실제 작도 좌표에서 파생되므로 임의는 아니지만, **한 시간틀만** 보여준다. 그래서 화면이 말하지 않는 것이 있다 — 같은 지표가 다른 시간틀에서는 **반대를 가리킬 수 있다**.

### 실측 — 스케일마다 방향이 실제로 뒤집힌다

`analyzeTrend` 장기창 기울기(%/봉), 프로덕션 실데이터 2026-08-28:

| 종목 | 120봉 | 600봉(판정) | 전량 |
|---|---|---|---|
| NVDA | +0.141% | +0.132% | +0.138% |
| TSLA | **−0.109%** | +0.132% | +0.149% |
| MSFT | +0.145% | +0.007% | +0.071% |
| BTC-USD | **−0.121%** | **−0.083%** | +0.095% |
| 005930(429봉) | +0.327% | +0.490% | +0.490% |

TSLA·BTC 는 좁게 보면 하락, 넓게 보면 상승이다. **이 충돌이 곧 정보다** — 지금 화면은 그중 하나만 보여준다.

### 함께 드러난 두 가지 (설계를 바꾼 실측)

1. **R² 로 스케일 간 우열을 매기면 안 된다.** 창이 커질수록 R²log 가 올라간다(전량 0.78~0.92 vs 120봉 0.16~0.58). 로그공간 장기 지수성장은 원래 잘 맞기 때문이다. 오늘 아침 "화면 밴드 밖 −59% 인데 R² 0.86" 과 같은 함정이다. → **스케일 간 강조는 R² 가 아니라 합류로 정한다.**
2. **짧은 이력은 3단이 무의미하다.** 005930(429봉)은 240봉부터 전량까지 완전히 같은 선이다. → **축약 규칙 필요.**

## 2. 범위

- **대상 지표 2종**: `trend`(추세선) · `fib`(피보나치). 구간을 잡아 그리는 지표라 스케일이 의미를 갖는다.
  나머지는 이번 범위 밖(오실레이터는 스케일을 바꿔도 같은 것을 다시 그릴 뿐이다).
- **시연 연출에 한정**. 정적 차트에서 스케일을 오가는 토글은 넣지 않는다(표면이 두 배가 된다).
  단, §4 의 계산은 순수 함수라 나중에 정적 노출로 재사용할 수 있다.
- **앱 시연 전용**. 카메라 연출(`_camTween`·`_regionForNode`)이 `forge-embed.js` 에만 있고
  PC `playAnalysis` 는 카메라를 움직이지 않는다. PC 시연에 카메라를 넣는 것은 별개 작업.
- **엔진 판정 불변**. 새 계산은 `run()` 이 부르지 않는다(작도 전용 — `collectAnchors` 선례).

## 3. 스케일 정의 (§1 확정)

| 단계 | 창 | 근거 |
|---|---|---|
| 좁게 | **120봉** | 기본 화면창(84~180봉)과 겹치는 "지금 보이는 구간" |
| 중간 | **600봉** | **판정 스케일** — 엔진이 실제로 쓰는 창(백테스트 LOOKBACK 600 정합, 엔진 1.11.1~1.11.2) |
| 넓게 | **전량** | 전체 맥락 |

중간을 600 으로 고정하면 **'판정 근거' 배지가 항상 가운데 단계**에 붙는다 — 종목마다 위치가 흔들리지 않는다.

**축약 규칙**(같은 선을 두 번 그리지 않는다):

```
P > 900        → 3단 (120 · 600 · 전량)
240 < P ≤ 900  → 2단 (120 · 전량)        ← 전량이 600 과 너무 가까워 별개 스케일이 아니다
P ≤ 240        → 1단 (전량)               ← 세 창이 사실상 같다
```

경계값 근거 둘:
- **900** = 600 × 1.5. 전량이 중간창의 1.5배는 돼야 다른 선이 나온다. 이 여유가 없으면 `P=700` 같은 종목이 600봉과 700봉을 나란히 그리게 된다 — 같은 선 두 번이다.
- **240** = 120 × 2. 좁게(120)가 별개 스케일이 되려면 전체가 그 두 배는 돼야 한다.

실측 대조: 005930(429봉)은 이 규칙으로 **2단**이 된다 — 120봉 +0.327%/봉과 429봉 +0.490%/봉은 실제로 다른 선이다(§1 표). 반면 240봉·600봉·전량은 429봉에서 모두 같은 선이라 하나로 접힌다.

## 4. 무엇을 강조할 것인가 (§2 확정)

2단계로 나눈다 — **스케일 안에서 걸러내고, 스케일 사이에서 강조한다.**

### A. 스케일 내 유의성 — 기존 게이트 재사용

- **추세선**: `R²log ≥ 0.15`(현행 weak 문턱) ∧ `trendScreenFit.onScreen`(2026-08-28 신설 화면 적합도).
- **피보나치**: 핵심 비율(`KEYR`·`KEYE`) + `collectLevels` significance.

**미달이어도 지우지 않고 흐리게 남긴다.** MSFT 600봉은 R² 0.01 인데, 그건 *"판정 스케일에 추세가 없다"* 는 정보다 — 없애면 그 사실이 사라진다.

### B. 스케일 간 합류 — 기존 규약 재사용

`forge-draw.js` 의 교차-degree 합류 규칙을 그대로 쓴다:

```
tol = (비교 대상 가격들의 범위) × 0.012      // 1.2%
2개 이상 스케일이 tol 안에 모이면 = 합류 → 최강 강조
```

**추세선은 점이 아니라 선**이므로 **현재 시점(마지막 봉)에서의 선 값**으로 비교한다. 세 스케일의 추세선이 지금 같은 가격대를 지나면 합류다.

### C. 방향 충돌 요약 — 부호에서 기계적으로

세 스케일의 기울기 부호를 그대로 적는다: `좁게 ▼ · 판정 ▲ · 넓게 ▲`

해석 문구는 **부호 조합에서 기계적으로** 나온다. 조합마다 그럴듯한 이야기를 붙이지 않는다:

| 조합 | 문구 |
|---|---|
| 셋 다 같음 | `세 시간틀 모두 {방향}` |
| 좁게만 다름 | `장기 {방향} 속 단기 {반대} — 되돌림 구간` |
| 넓게만 다름 | `장기 추세와 어긋나는 최근 {방향}` |
| 그 외(판정만 다름 등) | 부호 나열만 — **해석 없음** |

`{방향}` = 상승/하락. 부호 판정 문턱은 기존 작도 규약과 같은 `±0.05%/봉`.

## 5. 카메라·연출 (§3 확정)

### 축 전환 — 기존 규칙의 적용 범위만 바꾼다

`forge-app.autoLogForTicker` 가 이미 `max/min > 4` 면 로그축을 켠다. **새 규칙을 만들지 않고 판정 대상만 "전체 시계열" → "현재 창"** 으로 바꾼다. 결과적으로 좁게는 대개 선형, 넓게는 로그가 자동으로 나온다.

### 340봉 상한 — 로그축일 때만 해제

`_frameFromRegion` 의 `Math.min(N, 340, …)` 은 *"그 이상 넓히면 급등주는 최근 캔들이 위로 눌려 안 읽힌다"* 가 이유였다. 그건 **선형축의 문제**다. 로그축이면 상한을 푼다.

**후퇴 조건(구현 시 실측으로 판정)**: NVDA·TSLA 넓게 단계를 스크린샷으로 확인해 최근 구간이 읽히지 않으면 **넓게를 1,200봉으로 낮춘다**(전량 대신). 판단 기준은 "최근 120봉의 캔들 몸통이 세로로 구분되는가".

### 타이밍

현재 지표당 예산: `per = clamp(560, _playTotalMs / 노드수, 1300)ms`.

**3단 지표를 3단계로 세어 예산을 나눈다** — 분모를 `노드수` 에서 `총 단계수`(= 노드수 + 3단 지표당 +2)로 바꾼다. 각 단계가 정상 속도를 유지하고 전체 시연은 4단계분(약 2~5초)만 길어진다. 단계를 쥐어짜 빨라지는 것보다 낫다.

### 최종 상태

넓게 단계에서 **세 스케일을 겹쳐** 그리고 합류를 최강 강조 + 방향 요약 한 줄. 그 뒤 다음 지표로 넘어간다(그 지표의 카메라가 이어받는다). 마지막 지표면 기존 종료 동작(`_embFinish`)을 그대로 탄다.

## 6. 정직 표기 (협상 불가)

- **'판정 근거' 배지는 중간(600봉) 스케일에만.** 좁게·넓게는 `맥락 · 판정 미반영`.
- 각 선의 라벨에 **몇 봉을 잰 것인지** 항상 표기한다 — 오늘 확립한 규약 그대로:
  `장기 600봉 +0.13%/봉 R²0.80`.
- 방향 요약은 실측 부호 나열 + 표의 고정 문구만. 조합에 맞는 문구가 없으면 **나열로 끝낸다**.

## 8. 검증 (§4 확정)

**순수 함수 테스트**:
- `scaleSet`: `P=5030→[120,600,전량]` · `P=429→[120,전량]` · `P=800→[120,전량]` · `P=200→[전량]` · 경계 `P=240`·`P=241`·`P=900`·`P=901`

## 9. 열린 미결 (구현 중 확정)

- 넓게 단계의 창: **전량 vs 1,200봉** — §5 후퇴 조건의 스크린샷 판정으로 정한다.
- 겹침 단계에서 좁게·중간 선의 투명도 — 기존 위계 규약(강조/디밍) 안에서 조정.
- 피보나치 3단의 스윙 선택: `win` 안에서 `detectSwings` 가 잡는 스윙이 스케일마다 달라진다. 스케일별로 **가장 큰 스윙 하나**만 쓸지, 여러 개를 겹칠지는 첫 스크린샷을 보고 정한다.
