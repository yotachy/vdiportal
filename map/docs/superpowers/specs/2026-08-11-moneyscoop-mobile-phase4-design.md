# 머니스쿱 모바일 Phase 4 — 차트 줌 (두 손가락 핀치)

- 날짜: 2026-08-11
- 대상: `map/mobile/www/chart-zoom.js`(신규) · `screens/report.js` · `style.css` · `index.html`
- 선행: [`2026-08-10-moneyscoop-mobile-phase3-design.md`](2026-08-10-moneyscoop-mobile-phase3-design.md)
- 상태: 설계 승인됨 (2026-08-11)

## 1. 배경 — 실기기에서 나온 세 번째 불만

Phase 2를 폴드7에서 확인한 사용자 판단은 셋이었다. 둘(가려진 값·좁은 예측 구간)은 Phase 3이 다뤘고, 남은 하나가 이것이다:

> "확대도 단순히 이미지 확대 느낌이야. 차트의 확대가 아니고." — "고정된(죽어있는) 데이터 차트 같다"

정체는 명확하다. **모바일엔 차트 창 상태가 아예 없다.** `chart-layout.js`는 `tailBars` 상수를 받아 `fiMin = n - tail`을 계산할 뿐이다. 그리고 `index.html`에 핀치를 가로챌 장치가 없어 두 손가락 제스처가 브라우저 페이지 줌으로 빠진다 — 그게 "이미지 확대 느낌"이다.

PC는 이미 갖고 있다: `forge-app.js`의 `_chartWin{start,count}` + 휠 줌(:1095) + 두 손가락 핀치(:1112-1136) + 시간축 팬(:1161-1209).

## 2. 범위 — 줌만, 팬은 안 한다

**넣는다**: 두 손가락 핀치로 보이는 봉 수 변경 · 봉폭 기준 한계 · 캔버스 한정 페이지 줌 차단.

**넣지 않는다**: 시간축 팬 · 휠 줌(폰엔 휠이 없다) · 로그축 · 종목별 줌 기억.

### 2.1 팬을 빼는 이유 — `nowFi`가 둘로 갈라진다

`nowFi`는 모바일 코드 15곳에서 **두 가지 뜻**으로 쓰인다:

- **마지막으로 보이는 봉** — 캔들 루프 상한(`chart-draw.js:26`, `draw-layers.js:138`)
- **최신 봉** — 골드 현재가 태그(`chart-draw.js:146`), MA 마지막값(`:169`), seam 위치(`:65`), 예측 부착점(`:43`)

지금은 창이 항상 오른쪽 끝에 붙어 있어 둘이 같은 값이라 문제가 없다. **팬을 넣는 순간 갈라진다** — 과거로 밀면 "보이는 마지막 봉"은 과거인데 "최신 봉"은 화면 밖이다. 구분하지 않으면 현재가 태그가 과거 봉에 붙는 식으로 **조용히 틀리게** 그려진다. PC는 `forge-draw.js:983`의 `atLatest`로 처리한다(창이 최신 봉을 포함하지 않으면 예측을 아예 안 그림).

줌만 넣으면 창은 계속 오른쪽에 붙어 있으므로 이 모호성이 생기지 않는다. **`count` 하나가 곧 줌 레벨이고, `_chartWin` 전체는 필요 없다.**

대가는 명확하다 — 과거로 거슬러 올라갈 수 없다. 멀리 보려면 오므려야 한다. 팬이 정말 필요한지는 실사용으로 판단한다.

## 3. 상태

`report.js`의 `TAIL_BARS`를 상수에서 변수로 바꾼다. 화면 유지 중에는 줌이 유지되고, 종목을 바꾸거나 재진입하면 기본값으로 돌아간다. 종목별 줌 기억은 v1에 불필요하다.

## 4. 한계 — 봉폭으로 자르되, 기본값은 봉 수로

**이 둘을 갈라야 한다.** 기본까지 봉폭 기준으로 하면 펼침에서 197봉이 되고 예측 비중이 28% → 11%로 떨어져 **Phase 3에서 고친 것이 원상복구된다.**

```js
dx   = plotW / (tail + futW)                    // 봉 하나의 폭. plotW = W - 2*pad - axisW
tail ∈ [ plotW/12 - futW , plotW/2 - futW ]     // 봉폭 12px ~ 2px
tail ∈ [ 20, 400 ]                              // 절대 가드(위 범위에 다시 적용)
기본 = 60봉 (화면폭 무관 고정)
```

실측(`futW=24`, `pad=10`, `axisW=44`):

| 화면폭 | plotW | 최소 봉수 | 최대 봉수 | 60봉 봉폭 |
|---:|---:|---:|---:|---:|
| 373 (커버) | 309 | **20** | **131** | 3.68px |
| 673 | 609 | 27 | 281 | 7.25px |
| 884 (펼침) | 820 | **44** | **386** | 9.76px |

- **하한 봉폭 2px** — 그 아래서는 몸통과 심지가 구분되지 않아 캔들이 얼룩이 된다(240봉 = 1.17px, Phase 3 실측).
- **상한 봉폭 12px** — 더 벌리면 캔들이 비정상적으로 뚱뚱해진다. 커버에서는 20봉 가드가 먼저 걸리고, 펼침에서는 44봉이 하한이 된다.
- **기본 60봉 고정** — 어느 화면에서든 예측 비중 28%가 유지된다(Phase 3의 결론).

### 4.1 폴드 전개 시 재클램프 — 빠뜨리면 조용히 깨진다

한계가 `plotW`에 딸려 있으므로 **화면폭이 바뀌면 현재 봉 수가 새 한계 밖으로 벗어날 수 있다.** 커버에서 20봉으로 당겨 본 뒤 펼치면, 펼침의 하한은 44봉이라 20봉은 범위 밖이고 봉폭이 24px가 된다.

`report.js`의 `onResize`는 지금 폭이 바뀌면 `relayout()`만 부른다. **여기서 현재 `tail`을 새 `plotW` 기준으로 다시 클램프해야 한다.** 폴드는 두 화면을 상시로 오가므로 이건 예외가 아니라 일상 경로다.

## 5. 페이지 줌 — `user-scalable=no`를 쓰지 않는다

캔버스에만 `touch-action: pan-y`를 건다(`.rp-chart canvas`, 현재 이 속성 없음).

`user-scalable=no`는 페이지 전체의 브라우저 줌을 죽인다 — 시력이 나쁜 사용자가 리포트 본문을 확대할 수단을 잃는 접근성 후퇴다. `pan-y`는 셋을 동시에 만족한다:

- 캔버스 위 핀치가 브라우저 줌으로 새지 않고 우리 핸들러로 온다
- **세로 스크롤은 살아 있어** Phase 1의 350ms 홀드 계약이 그대로 유지된다(`pointermove`가 홀드 전엔 `preventDefault`를 부르지 않는 구조)
- 차트 밖에서는 페이지 줌이 정상 동작한다

## 6. 제스처 — 두 손가락만

한 손가락은 지금 그대로다. 페이지 스크롤 + 350ms 홀드 크로스헤어. **Phase 1의 홀드 계약을 건드리지 않는다**(사용자 결정, Phase 3 §7).

```
touchstart (2점) → dist0 · tail0 기록 · 대기 중인 홀드 타이머 취소
touchmove  (2점) → ratio = dist0 / dist  →  tail = clamp(round(tail0 × ratio))
touchend/cancel  → 해제
```

벌리면 `dist`가 커져 `ratio < 1` → 봉 수 감소 = 줌인. PC(`forge-app.js:1129`)와 같은 식이다.

PC는 핀치 중심 아래 봉을 고정하려고 `rel`·`bi`를 계산하지만 **우리는 오른쪽 끝 고정이라 그 계산이 필요 없다.** 팬을 안 넣은 대가로 얻는 단순함이다.

**두 번째 손가락이 닿는 순간 홀드 타이머를 취소해야 한다.** 안 그러면 핀치 도중 크로스헤어가 켜진다. `preventDefault`는 `e.cancelable`일 때만 부르고, 리스너는 `{passive:false}`로 등록한다.

## 7. 재도장

`tail`이 실제로 바뀐 프레임에서만 `relayout()` + `frame(null)`. `requestAnimationFrame`으로 스로틀한다(크로스헤어의 `scheduleFrame`과 같은 방식). `relayout()`은 이미 `TAIL_BARS`를 읽으므로 그 값이 변수가 되는 것으로 충분하다.

## 8. 배치

```
mobile/www/
  chart-zoom.js     신규 — 순수 함수. 클램프 · 핀치 수학
  chart-layout.js   수정 — plotW 계산을 노출(plotWidth(W, pad))
  screens/report.js 수정 — tail 상태 · 터치 리스너 · onResize 재클램프
  style.css         수정 — .rp-chart canvas { touch-action: pan-y }
  index.html        수정 — chart-zoom.js 스크립트 태그
```

제스처 배선은 DOM이라 테스트할 수 없지만 **계산은 순수 함수로 떼어내 값으로 검증한다.** Phase 3의 `MSLegend.rows`와 같은 갈래다.

```js
MSZoom = {
  limits(plotW, futW) -> { min, max }              // 봉폭 12px~2px → 봉 수 범위, [20,400] 가드
  clamp(plotW, futW, tail) -> number               // 범위 밖이면 끌어당김
  fromPinch(tail0, dist0, dist) -> number          // 클램프 전 원시 봉 수
  DEFAULT_TAIL                                     // 60
}
```

`plotW`는 `chart-layout.js`가 쓰는 것과 같은 식(`W - 2*pad - axisW`)이어야 한다 — 두 곳에서 따로 계산하면 갈라진다(Phase 3에서 두 번 데었다). **`chart-layout.js`가 `plotW` 계산을 노출하고 `chart-zoom.js`가 그것을 쓴다.**

## 9. 테스트

| 대상 | 고정하는 것 |
|---|---|
| `limits` | 화면폭별 상·하한(373→20/131, 884→44/386) · `[20,400]` 가드가 실제로 무는 경우 |
| `clamp` | 범위 밖 입력을 경계로 · 범위 안 입력은 그대로 · 경계에서 실제 봉폭이 2~12px |
| `fromPinch` | 벌리면 감소·오므리면 증가 · 단조 · `dist=0`·음수·NaN에 안 죽음 |
| 기본값 불변식 | 어느 화면폭이든 기본 60봉 · 예측 비중 28% 유지 — **Phase 3 회귀 방지** |
| 봉폭 불변식 | 클램프 범위 전 구간에서 `chartLayout`이 내는 실제 봉폭이 2~12px |
| `plotW` 단일 출처 | `chart-zoom`이 쓰는 `plotW`가 `chartLayout`의 것과 일치 |
| 재클램프 | 373에서 20봉 → 884로 바뀌면 44봉으로 끌어올려짐 |

**변이 검증 필수.** Phase 2·3에서 깨진 구현에 통과하는 테스트가 여러 건 나왔다. 각 테스트는 그것이 지킨다고 주장하는 것을 실제로 깨뜨려 확인한 뒤에만 통과로 친다.

전체 관문은 `map/tests/run.sh`(현재 508건).
