## 1. 배경 — 펼친 화면이 그냥 늘어난다

`style.css`에 **미디어쿼리가 하나도 없다.** `app.js`는 루트에 화면 하나만 그린다. 폴드7을 펴면 워치리스트 행과 리포트 텍스트가 749px로 늘어나고, 큰 화면이 주는 것은 "같은 것이 더 넓게"뿐이다.

Phase 0에서 커버(411×814)만 재고 펼침은 안 쟀다(`phase0-measurements.md:25`). 이번에 실측했다.

## 2. 실측 (2026-08-11, 폴드7 · 폰 Chrome)

| 상태 | CSS px |
|---|---|
| 커버(접힘) | **411 × 814** |
| 펼침 | **749 × 654** |

**이 값이 설계의 전제를 하나 뒤집었다.** 펼침은 "커진" 것이 아니라 **짧고 넓어진** 것이다 — 가로 +82%, **세로 −20%**. 749는 안드로이드 medium 구간(600–839)의 아래쪽이다.

### 2.1 폭 예산 — 목록과 차트가 경쟁한다

749에서는 "목록도 두고 차트도 키운다"가 성립하지 않는다. 셋 중 하나다.

| 안 | 목록 / 리포트 | 콘텐츠 폭 | plotW | 봉 폭(60봉) |
|---|---|---|---|---|
| 커버(기준) | — | 371 | 305 | 3.67px |
| A 원안(목록 320) | 320 / 428 | 388 | 322 | 3.88px (+6%) |
| **A′ 채택(목록 압축)** | **255 / 493** | **453** | **387** | **4.66px (+27%)** |
| D 세로 2단(단일 컬럼) | — / 749 | 709 | 643 | 7.75px (+111%) |

`plotW = (콘텐츠 폭 − 카드 보더 2) − 2·pad(10) − axisW(44)`, 봉 폭 `= plotW / (tail 60 + fut 23)`. 가격축과 패딩이 고정 오버헤드라 콘텐츠 폭 증가(+22%)보다 봉 폭 증가(+27%)가 크다.

**A′를 고른 이유**: 이 앱의 실사용은 "여러 종목을 훑으며 판정 비교"다(워치리스트 스캔이 그 증거). 단일 컬럼에선 종목마다 뒤로가기가 강제된다. D는 차트를 두 배로 키우지만 그 왕복을 그대로 남긴다. A′는 목록에서 실제로 덜 중요한 것(64px 스파크라인·확신 숫자)을 덜어 왕복 제거와 차트 +27%를 동시에 가져간다.

## 3. 모드 판정

```
2단 조건: (min-width: 600px) and (min-height: 480px)
```

**높이 조건이 핵심이다.** 커버를 눕히면 814×411이 되어 폭 조건만으로는 2단에 걸리는데, 높이 411에 두 칸을 세우면 리포트를 못 쓴다.

| 기기 상태 | 크기 | 모드 |
|---|---|---|
| 커버 세로 | 411 × 814 | 단일 |
| 커버 가로 | 814 × 411 | **단일** (높이 411 < 480) |
| 펼침 세로 | 749 × 654 | 2단 |
| 펼침 가로 | 654 × 749 | 2단 |

전환은 `matchMedia(MODE_QUERY).addEventListener("change")` — resize마다가 아니라 **경계를 넘을 때만** 재구성한다.

### 3.1 경계값은 한 곳에만 산다

브레이크포인트가 CSS `@media`와 JS `matchMedia`에 각각 적히면 **두 출처가 갈라진다** — 한쪽만 고치면 JS는 2단이라 믿는데 CSS는 단일로 그리는 상태가 조용히 생긴다. Phase 3의 상태 어휘 표기가 정확히 이 모양으로 갈렸다.

따라서:

```js
MIN_W = 600, MIN_H = 480                                  // 유일한 출처
MODE_QUERY = "(min-width: " + MIN_W + "px) and (min-height: " + MIN_H + "px)"
isDual(w, h) = w >= MIN_W && h >= MIN_H                   // 같은 상수를 읽는다
```

**CSS는 자기 미디어쿼리를 갖지 않는다.** JS가 `<body>`에 `ms-dual` 클래스를 붙이고, 모든 2단 스타일은 `body.ms-dual ...`로 건다. 런타임 판정은 `matchMedia`, 테스트 대상은 `isDual`, 스타일은 클래스 — 셋이 상수 두 개를 공유한다.

## 4. 기하

```
listWidth(totalW) = clamp(240, round(totalW × 0.34), 300)     // 749 → 255
chartHeight(dual, vh) = dual ? clamp(320, vh − 240, 460) : 520 // 654 → 414
```

**차트 높이를 모드로 가르는 이유**: 커버의 520은 Phase 1~4가 검증한 값이라 건드리지 않는다. 세로 654인 펼침에서만 줄인다 — 520을 그대로 두면 뷰포트의 80%를 차트가 먹는다. 상수 240은 헤드·티어행·판정·레전드가 차지하는 세로 실측치다.

```
단일 모드 (커버 411×814)          2단 모드 (펼침 749×654)
┌───────────────┐                ┌────────┬──────────────────┐
│  워치리스트    │                │ 워치   │  리포트          │
│    또는       │                │ 리스트 │  (선택 종목)      │
│  리포트       │                │  255   │      493         │
│  (한 번에 하나)│                │        │  차트 높이 414    │
└───────────────┘                └────────┴──────────────────┘
                                   각 칸 독립 스크롤, body 스크롤 없음
```

## 5. 상태 모델 — 라우트를 버리고 선택 종목으로

```js
state = { selectedSym: "AAPL" | null, showing: "watchlist" | "report" }
```

- **2단**: 두 칸을 항상 그린다. 오른쪽은 `selectedSym`의 리포트, 없으면 빈 안내
- **단일**: `showing` 하나만 그린다 (현행 동작과 동일)

**접었다 펴도 보던 종목이 따라오는 것이 공짜로 나온다** — 같은 `selectedSym`을 레이아웃만 달리 그리기 때문이다. 라우트(`route: "report"`)를 유지한 채 2단을 얹으면 "왼쪽 칸은 무슨 라우트인가" 같은 무의미한 질문이 생긴다. 화면이 둘뿐이라 라우트가 벌어주는 것이 없다.

### 5.1 첫 진입

`MSStore.getLastSym()` 복원 → 워치리스트에 없는 종목이면(삭제됐으면) `null` 취급 → `null`이면 오른쪽 칸에 빈 안내.

**커버로 보다가 펴는 흐름이 지배적**이므로 그때는 이미 `selectedSym`이 메모리에 있다. 복원이 실제로 쓰이는 경우는 앱을 완전히 새로 켠 순간뿐이고, 그 드문 경우에 고르지도 않은 종목을 자동 분석해 띄우는 것(콜드 942ms)은 과하다.

### 5.2 선택 변경 시 목록 칸은 다시 그리지 않는다

오른쪽 칸만 교체하고, 왼쪽은 `data-sym` 속성으로 하이라이트 클래스만 옮긴다.

목록을 통째로 재렌더하면 ① 스크롤 위치가 맨 위로 튀고 ② **진행 중인 스캔 UI가 죽는다**(`MSWatchlist.render`가 `scanning=false`로 시작한다). 종목을 옮겨 다니는 것이 A′의 존재 이유인데 그때마다 목록이 튀면 안 된다.

렌더 단위는 둘이다:

- `renderShell()` — 모드 전환·부팅 시 두 칸 전부
- `renderReportPane()` — 선택 변경 시 오른쪽만 + 왼쪽 하이라이트 이동

## 7. 스크롤 구조

2단에서 `body`는 스크롤하지 않는다. 셸이 `height:100dvh` 그리드이고 각 칸이 `overflow-y:auto; overscroll-behavior:contain`이다.

- `env(safe-area-inset-bottom)`은 `body`에서 각 칸으로 옮긴다
- `app.js`의 `window.scrollTo(0,0)`은 2단에서 의미가 없다 — 해당 칸의 `scrollTop = 0`으로 바꾼다
- **캔버스의 `touch-action:pan-y`(Phase 4)는 스크롤 대상이 body에서 칸으로 바뀐다.** 사양상 가장 가까운 스크롤 조상을 따라가므로 Phase 1의 350ms 홀드 계약은 유지돼야 한다 — 다만 코드로 검증되지 않는다(§10)

## 9. 범위 밖

- **3단·확장(≥840px) 레이아웃** — 폴드7이 749라 실측 근거가 없다
- **커버 가로회전의 520px 차트** — 뷰포트 411에 차트 520이 들어가는 것은 **현행에도 있는** 선행 결함이다. 모드 판정이 커버 가로를 단일로 떨어뜨리므로 Phase 5가 만들지도, 바꾸지도 않는다. 백로그로 이월
- **워치리스트 기능 변경** — 압축은 표시만, 동작 무변경
- **종목별 줌 기억** — Phase 4에서 이미 범위 밖으로 정리됨

## 10. 실기기 확인이 필요한 항목

코드로 검증되지 않아 사람이 확인해야 한다.

1. 펴면 2단, 접으면 단일로 바뀌고 **보던 종목이 양방향으로 따라온다**
2. 왼쪽 목록에서 다른 종목을 눌러도 **목록 스크롤 위치가 유지**된다
3. 스캔 중에 종목을 눌러도 진행 표시가 안 죽는다
4. 차트 위 한 손가락 세로 드래그로 **오른쪽 칸이** 스크롤된다(body 아님)
5. 차트 위 350ms 홀드 크로스헤어가 2단에서도 동작한다(Phase 1 계약)
6. 두 손가락 핀치 줌이 2단에서도 동작한다(Phase 4 계약)
7. 목록을 스크롤해도 리포트 칸이 따라 움직이지 않는다
8. 커버를 눕혀도 2단으로 넘어가지 않는다
9. 모드를 여러 번 오가도 차트가 정상이다 — `activeResizeCleanup`이 리스너를 하나로 유지하는지(Phase 1에서 누수로 한 번 고친 자리)

## 11. 열린 항목

- **모드 전환 시 리포트가 재분석된다.** `report.js`의 `cache` Map이 OHLC를 들고 있어 네트워크는 안 타지만 `analyzeFull`은 다시 돈다(~50ms 추정, 폴드7 실측 아님). 전환이 잦은 기기라 체감되면 분석 결과까지 캐시할 것
- **목록 255px에서 종목명 잘림.** `.wl-name`이 ellipsis라 깨지지는 않으나 긴 이름("NVIDIA Corporation")은 대부분 잘린다. 실기기에서 판단
