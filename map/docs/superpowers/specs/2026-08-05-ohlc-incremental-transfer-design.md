# OHLC 증분 전송 — 설계

- 날짜: 2026-08-05
- 대상: `forge-api.php`(OHLC 프록시) · `forge-app.js`(`fetchOHLC`)
- 상태: 설계 승인됨

## 1. 배경

사용자 요구: "기존에 받은 종목 차트 데이터는 서버에 저장하고, 새로 업데이트가 필요한 주가정보만 추가하는 식으로 관리."

**서버↔외부 API 구간은 이미 그렇게 동작한다**(커밋 `f5ff27b`, `forge-api.php:64~175`):

- TTL(일봉 1h / 주·월 6h) 내면 캐시 파일 반환, 외부 호출 0
- TTL 만료 시 누적 캐시를 읽고 TwelveData에 `outputsize=300`만 요청(전량 5000 대신)
- `t` 기준 머지(같은 t=갱신, 신규만 추가), 최대 6000봉 누적
- 수집 실패 시 누적 캐시로 폴백

라이브 실측으로 동작을 확인했다 — AAPL이 `source=twelvedata+inc`로 5013봉(2006-08-29~2026-08-04) 누적.

**남은 비효율은 클라이언트↔서버 구간이다.** 서버는 증분으로 쌓는데, 클라는 매 요청마다 누적 전량을 받는다.

### 실측 (2026-08-05, 라이브)

| 종목 | 봉 수 | 매 요청 전송량 |
|---|---|---|
| AAPL | 5013 | 403,859B |
| BTC-USD | 3265 | 271,281B |
| 005930 | 413 | 30,547B |

```
AAPL 원본 403,859B → gzip 105,498B  (26.1%, 3.8배)
봉당 평균 81B → 델타 3봉이면 약 242B
```

원인 셋:

- `fetchOHLC`가 `{cache:"no-store"}`로 브라우저 캐시를 명시적으로 끔 (`forge-app.js:1855`)
- 응답에 gzip 미적용 — `Accept-Encoding: gzip`을 보내도 403,859B 그대로, `Content-Encoding` 헤더 없음
- 클라 세션 캐시 없음 → 종목 A→B→A 전환 시 A를 다시 받음

발생 빈도가 높다. `fetchOHLC` 호출 지점 7곳이 전부 재요청 경로다: `loadDoc` 자동 재fetch(종목 전환마다), `loadTicker`, `chartSetTF`, 대시보드 매트릭스, `rankMomentum`(워치리스트 N종목 순차 N회), 벤치마크 로드, 노드 불러오기.

## 2. 목표

- 전송량 절감 (체감: 종목 전환 속도)
- 외부 API 호출 절감 (TwelveData 무료 크레딧 보호)

목표치: 흔한 경우 **403,859B → 0B(캐시 히트) 또는 ~242B(델타)**. 첫 로드만 gzip 적용된 ~105KB.

## 3. 설계

`fetchOHLC`가 7개 호출 지점의 **단일 관문**이라는 점을 이용한다. 이 함수 한 곳에 캐시를 넣으면 7경로가 동시에 해결된다.

### 3.1 서버 — `?since=` 필터

```
GET forge-api.php?ohlc=1&symbol=AAPL&tf=1day&since=2026-08-01
→ { ok, symbol, tf, source, name, full: false, candles: [2026-08-01 이후 봉] }
```

**`since`는 응답 필터일 뿐이며, 캐시 파일에는 항상 전량을 저장한다.** 잘라서 저장하면 누적본이 델타 요청 한 번에 소실된다. 이 구분이 안전의 핵심이다.

**`full` 플래그(신규)**: `false`면 델타(클라가 머지), `true`면 전량(클라가 교체). 서버가 `since`를 지키지 못한 모든 경우 — 형식 불량, 서버 캐시 없음, 첫 수집 — 에 `true`로 알려 클라가 조용히 어긋나지 않게 한다.

`since` 파라미터가 아예 없는 요청도 `full:true`로 응답한다(전량이므로). 즉 `full:false`는 "`since`가 적용된 델타"일 때만 나온다. 구버전 클라는 `full`을 읽지 않고 `since`도 안 보내므로 종전대로 전량을 받는다(하위호환).

새 봉이 없으면 `candles:[]` + `full:false`를 반환한다. 오류가 아니라 "변경 없음"의 정상 표현이다.

**비교 연산자는 `>=`** (린치핀):

`>`로 하면 오늘 진행 중인 봉의 종가 갱신을 영원히 받지 못한다. 클라가 보내는 `since`는 "내가 가진 마지막 봉의 날짜"인데 그 봉이 아직 안 끝났을 수 있다. `>=`로 그 봉을 다시 받아 덮어쓴다.

따라서 클라 머지는 단순 append가 아니라 **"같은 t는 교체, 새 t는 추가"** — 서버가 `forge-api.php:160~166`에서 이미 쓰는 규칙과 동일하다.

`since` 검증: `/^\d{4}-\d{2}-\d{2}$/`. 모든 소스의 `t`가 이 포맷이다(TwelveData `datetime`, Naver 조립, Stooq CSV[0]) — `tf`가 일/주/월로 제한되어 시각 성분이 없다.

TTL 히트 경로(`readfile($cf); exit;`)는 `since`가 있으면 디코드→필터로 갈라진다. `since`가 없으면 종전대로 `readfile` 직행.

### 3.2 클라 — `fetchOHLC` 캐시 관문

```js
_ohlcCache: Map("SYM|tf" → {candles, at, name, source})
신선도: 일봉 5분 / 주·월봉 30분
```

```
캐시 신선  →  네트워크 0, 즉시 반환
캐시 있음  →  ?since=<마지막봉 t> → 델타를 t-map 머지
캐시 없음  →  전량
fetch 실패 →  캐시 있으면 캐시 반환(stale), 없으면 현행대로 {ok:false}
```

**반환 shape은 현행과 동일하게 유지한다** — 호출자 7곳이 `r.ok`·`r.candles`·`r.name`·`r.tf`를 그대로 읽으므로, 캐시 히트든 델타 머지든 항상 **누적 전량이 담긴 `candles`**를 반환한다. 델타는 `fetchOHLC` 내부에서만 다루고 밖으로 새지 않는다. `cached`/`stale` 플래그는 부가 정보이며 기존 호출자는 무시해도 무방하다.

델타가 빈 배열이어도(`candles:[]`) 캐시의 `at`은 갱신한다 — "확인했고 변경 없음"이므로 신선도 시계를 다시 시작하는 것이 맞다.

**`force` 옵션**: `불러오기` 버튼(`loadTicker`)은 사용자가 명시적으로 누른 새로고침이므로 `{force:true}`로 신선도를 무시한다. 단 force가 끄는 것은 "네트워크 스킵"이지 "증분"이 아니다 — force여도 `since`는 그대로 보낸다.

**LRU 12종목 캡**: 워치리스트가 크면 Map이 무한정 자란다. AAPL 5000봉이 배열로 수 MB이고, 티커 노드의 `_series`/`_ohlc`와 중복 보유가 된다. Map의 삽입순 유지를 이용해 `size > 12`면 가장 오래된 키를 제거한다.

**`_dashCache` 흡수**: 대시보드 전용으로 따로 있는 캐시(`forge-app.js:1639`)를 이 캐시로 통합해 중복을 제거한다.

### 3.3 gzip

`forge-api.php` 최상단(출력 전) 한 곳:

```
Accept-Encoding에 gzip 포함 && zlib.output_compression 꺼짐 && 헤더 미전송
  → ob_start("ob_gzhandler")
```

`zlib.output_compression` 확인이 이중압축 방지책이다. 조건 불충족 시 무압축으로 정상 동작한다(graceful).

파일 최상단 1곳에 두어 GET/POST 공통 적용한다. 출력은 모든 경로에서 마지막 `echo`에 몰려 있어 쓰기 경로의 flock/원자 rename과 간섭하지 않는다(검증 항목 7).

## 4. 오류 처리

| 상황 | 동작 |
|---|---|
| `since` 형식 불량 | 무시하고 전량 + `full:true` |
| 서버에 캐시 없음(첫 요청인데 `since` 옴) | 전량 수집 후 전량 반환 + `full:true` |
| 델타가 클라 마지막 봉과 불연속 | 서버는 필터 결과를 그대로 반환. 클라 머지가 t-map이라 구멍이 나도 정렬은 유지 |
| fetch 실패 | 캐시 있으면 캐시 반환(`stale:true`), 없으면 `{ok:false}` — 현행 유지 |
| 오프라인 | 현행 `SERVER_OK` 폴백 경로 유지 |

## 5. 검증

로컬 PHP가 없으므로 라이브 curl이 관례다(프로젝트 기존 규율).

1. `since` 없이 전량 → 봉 수 기준값 확보
2. `since=최근일` → 델타만, `full:false`
3. `since=미래일` → 빈 배열
4. `since=쓰레기` → 전량 + `full:true`
5. `Content-Encoding: gzip` 실측
6. **델타 요청 후 전량 재요청 → 봉 수가 ①과 동일** ← 캐시 파일이 잘리지 않았는지 확인하는 최우선 회귀
7. 쓰기 op(문서 upsert) 회귀 — gzip 버퍼링이 flock/원자 rename 경로를 건드리지 않는지
8. `node --test forge-core.test.js` 246건

헤드리스는 읽기 경로만 사용한다. `fetchOHLC`는 읽기라 안전하지만 `loadTicker`는 사용자 데이터를 건드리므로 금지(기존 규율 유지).

## 6. 범위 밖 (YAGNI)

- **localStorage 영속** — 새로고침 후에도 델타만 받는 안. AAPL 하나가 394KB라 5MB 쿼터에 10종목이면 포화되고, 압축 저장·쿼터 초과 처리까지 붙는다. 새로고침은 세션당 몇 번뿐이라 비용 대비 이득이 가장 나쁘다.
- **델타 불연속 감지 후 자동 전량 재요청** — `full` 플래그로 어긋남을 이미 막고, t-map 머지라 구멍이 나도 정렬은 유지된다.
- **Naver·Stooq의 서버↔외부 증분** — Stooq는 전체 CSV가 한 요청이라 파라미터로 줄일 수 없고, Naver는 400봉 캡이라 절감폭이 작다. 이번 범위는 클라↔서버 구간이다.

## 7. 배포

- 대상: `forge-api.php` + `forge-app.js`
- **불가침**: `forge_ohlc_cache_*.json` 업로드 금지 — 이번 작업이 지키려는 누적 데이터 그 자체다. `forge_data.json`·`forge_images.json`·`forge_jobs.json`·`forge_td_key.txt`도 종전대로 금지.
