# 스쿱포지(PC 웹) 정보 구조 전수 조사

**목적** — 머니스쿱 모바일 앱을 처음부터 다시 만들기 위한 **원자료**. PC가 무엇을 알고, 무엇을 보여주고, 사용자가 거기서 무엇을 하는지를 사실 그대로 수집한 문서다. 화면 설계는 하지 않는다(§6·§7의 한 줄 판단 제외).

**조사 범위** — `forge.html`(291) · `forge-state.js`(757) · `forge-ui.js`(1,578) · `forge-draw.js`(3,449) · `forge-app.js`(3,856) · `forge-core.js`(2,757) · `forge.css`(1,749) · `forge-guide.html` · `forge-scorecard.html`. **`map/mobile/` 은 읽지 않았다**(폐기된 구현).

**엔진 버전** `1.11.0` · **지표** 32종 · **검증 축** 8종(`validatedAxes`) · 조사일 2026-08-19.

## 1. 엔진이 산출하는 것 전부 — `ForgeCore.run()` 반환 구조

### 1-6. 지표별 `analyzeX()` — 대표 5종 구조

| 지표 | 반환 구조 | 핵심 필드 의미 |
|---|---|---|
| `analyzeMA(price,{len,ema})` | `{mas:{short,mid,long}, cross:{type,barsAgo}, align:{order,score}, sr:{ma,side,distPct}, bias}` | `mas.*` = `{period, series[], slope(−1..1, 실현변동성 정규화), last}` · `cross.type` = `golden`/`dead` · `align.order` = `bull`/`bear`/`mixed` · `sr.side` = `support`/`resistance` · `bias = 0.5·정배열 + 0.3·교차(감쇠) + 0.2·장기기울기` |
| `analyzeRSI(price,{period})` | `{series[], last, zone, trend, cross50, regime, divergence:{type,pricePts}, bias}` | `zone` = `overbought`/`oversold`/`neutral` · `divergence.type` = `bullish`/`bearish`/null + 가격축 두 점(차트에 점선으로 그림) |

| `analyzeStructure(price,{swing,draw})` | `{swings[{idx,price,type}], trend, event, swingHigh, swingLow, bias, tiers?}` | `event` = `BOS_up`/`BOS_down`/`CHoCH_up`/`CHoCH_down`/`none` · bias는 이벤트별 고정값(BOS ±0.6, CHoCH ±0.5, 추세 ±0.3) · `draw:true`면 다중스케일 `tiers` 추가 |

> **공통 규약**: 방향 지표는 전부 `bias ∈ [−1, 1]`. `analyzeATR`은 `bias: 0` 고정(변동성 전용), `analyzeTrend`는 `bias` 필드 자체가 없다(방향은 `blend.slopeLog`).

### 1-7. `run()` 내부의 예측 합성 규약 (모바일이 반드시 알아야 할 것)

- 지표 29종이 각각 `bias × trendProfileForTF(tf).trendScale × cap`(±4%~±10%)의 **드리프트 항**을 낸다.
- 합은 **예상(agree) / 반대(oppose)로 분리**: `_auxCap = 방향 × max(0, min(0.05, 예상합) − 0.5×반대합)`. 반대 지표는 캡에 가려지지 않고 **항상 절반 가중으로 되돌림**을 만든다 — 이것이 PC의 "반대 의견"의 수치적 실체다.
- 전체 드리프트 합은 ±0.28 캡.
- 종합 방향과 반대로 크게 드리프트하면 ×0.25로 억제(`_dirSig<−8 && m>0` 등) — "지표 종합=하락인데 상승확률 86%" 모순 억제.
- 콘 폭 = `√(sigBand² + 0.36·trChSig²) × √k × 0.85 × 0.75(_CONE_CAL) × bandScale × GARCH볼팩터 × _coneVolMult(일봉)`.
- **미사용/저사용 산출물**(모바일엔 기회): `counterBasis`, `prediction.levels`(레벨 목록), `signal` 시계열, 오버레이 8종의 `values`(항상 0).

### 3-2. 웹분석 vs 시뮬레이션 — 결정적 차이

| | **웹분석** `runEngine()` (forge-app.js:2264) | **시뮬레이션** `playAnalysis()` (forge-app.js:2771) |
|---|---|---|
| 성격 | 심층 계산 | **같은 결과를 산출 과정으로 재생**(웹분석의 하위 기능, 결과 동일) |
| 선행 | stale 가드(심볼 바뀌었으면 먼저 재로드), **SPY + 섹터 ETF 벤치마크 로드** | 내부에서 `runForge()` 먼저 호출 |
| 계산 | `runForge()` → `ForgeCore.run()` 1회 | `ForgeCore.runSteps()` — **노드를 1개씩 늘려가며 N회 `run()`** |
| 추가 | 멀티TF 매트릭스(`scheduleDash` → 일·주·월 각각 fetch+run) · 상대강도 2축 활성 · `_deepSessionDocs`에 등록(흑백 해제 → 컬러) | 없음 |
| 기록 | **`logPrediction()`** — 서버 원장에 예측 적재(방향·up·8축 확률·asOf·futW), 만기 후 자동 채점 | 없음 |
| 진행 표시 | 오버레이 게이지 950ms · 3단계 문구(`지표 계산 중… → 예측 시나리오 산출 중… → 종합 판정 중…`) | 아래 리빌 시퀀스 |
| 종료 | 토스트 `웹분석 완료 · 포지결과 갱신` | 토스트 `포지 완료 · N개 지표 결합 → 시그널 S` |

**시뮬레이션이 보여주는 것 — 순서 (모바일 "분석 과정" 화면의 원형)**

1. **대상 확정** — `indNodes` = 지표 노드 중 **레일에서 표시 중인 것만**. 32종 전부가 아니라 사용자가 고른 조합.
2. **초기화** — 근거 작도 클립 0, 예측 콘을 **anchor 평면으로 접음**(`flat`), 레이더 막대 전부 흐림, 지표 신호 전부 흐림, 오실레이터 비움, 진행 로그 비움.
3. **틱 시퀀스** — 지표마다 `analysisSteps(n)`이 **다단계 서술**을 낸다(MA는 5단계, 그 외는 지표별 `xSteps`). 모든 단계를 평탄화해 `ticks[]` 생성. 간격 = `clamp(16000/틱수, 150ms, 620ms)` → **총 ~16초 목표**.
4. **틱마다**:
   - 새 지표 시작이면: 이전 지표 `analyzed` 처리, 현재 지표 `analyzing` 점등, `_evidenceSet`에 추가
   - **레이더 막대 점등** + **지표 신호 행 점등**(그 지표만)
   - **HUD**: 지표명 + 하위 단계 칩 순차 점등 + 사용자 메모 + `N/총개수` 세그 진행바
   - **진행 로그**: `[지표] 단계 문장` 한 줄 append (그 지표의 **마지막 단계 = 결론**은 강조)
   - 상단 진행 문구: `분석 중 3/19 · 볼린저밴드 (2/4)`
5. **동시 모핑**(RAF, 총 = 틱 전체 시간 + 800ms):
   - **근거 작도가 손그림처럼 그어짐** — 모든 도구가 동시에, 진행도 `_scanU`에 따라. **중요도(weight+|conviction|)가 높은 지표일수록 먼저·빠르게 완성**
   - **예측 콘이 평면에서 최종 경로로 펼쳐짐**(`lerpPred(flat, finPred, e)`)
   - **오실레이터가 좌→우로 그려짐**
   - **판정 스트립이 0→최종으로 충전**(국면·확률·시그널·목표가 단조 증가)
   - **예측 시점별 표 게이지 충전**, **매트릭스 카드 게이지 충전**
   - 작도 ~28fps 스로틀, DOM 게이지 ~14fps 스로틀
6. **종료** — 전 지표 `analyzed`, 중심 포지 노드 점등, 전체 확정 재렌더, HUD에 **종합 결론 카드**(`N개 지표 결합 · 국면 X · 목표가 T · 시그널 S`).
7. **모션 축소 선호 시** — 애니메이션 전부 건너뛰고 즉시 최종 결과 + 토스트.

## 5. PC가 보여주는 "판정"과 "근거"의 구조

### 5-1. 종합 판정이 나오는 경로

```
32개 지표 analyzeX() → bias ∈ [−1,1]
      │
      ├─ ① _biasAvg = 평균 bias                        ─┐
      ├─ ② _trendDir = clamp(trS / 0.008, −1, 1)        ─┤ ③ _dirSig = (①×0.66 + ②×0.34)×100 + conviction×0.5
      │                                                  │       └ 하락 예측 정직화: 200MA 비하락이면 ×0.35 후 상승 전환
      │                                                  │
      ├─ ④ 지표별 드리프트 = bias × trendScale × cap    ─┤ ⑤ 예상/반대 분리 → _auxCap = dir×max(0, min(0.05,예상합) − 0.5×반대합)
      │                                                  │
      └─ ⑥ 콘 폭 = f(σ, 채널σ, ATR, GARCH, _coneVolMult) ┘
                                                          │
   예측 경로 path[k] = anchor·exp(평균회귀 + 모멘텀 + 추세 + 신호 + 계절 + 질감 + _auxCap·k/futW)
                                                          │
   regime = _dirSig > 12 ? bull : < −12 ? bear : neutral
   score  = round(_dirSig)
   상승확률 = aggUpProb(prediction) = Σ upProb(path[k], hi[k], anchor)/√(k+1) → Platt 캘리브레이션
```

### 5-2. 지표별 신호 집계 — 세 갈래

| 경로 | 함수 | 어디에 |
|---|---|---|
| **A. 방향·강도** | `_nodeBias(n, price)` (forge-ui.js:511) — 지표별 `analyzeX().bias` 직접 호출, 프레임 캐시(`_an`) | 지표 방향·강도 레이더(길이=강도) · 지표 신호 리스트(화살표+바) · 판독문 뱃지 · 판정 스트립 `방향 ▲a·–b·▼c` |
| **B. 사실 서술** | `nodeExpert(n, result, price, last)` — 지표별 3줄 사실 배열. 대부분 `ForgeCore.xSteps(...)` 를 `slice(1,4)` 한 것 | 노드별 전문 분석 카드 · 지표 신호 행의 판정 문장 |
| **C. 시연 서술** | `analysisSteps(n, ...)` — 지표별 다단계(레이어 번호 포함). MA는 5단계 | 시뮬레이션 HUD 단계 칩 + 진행 로그 |

> **A·B가 서로 다른 함수라는 점이 중요**하다. 화살표(방향)는 `_nodeBias`, 문장은 `nodeExpert`. 과거에 문장이 방향을 단정해 화살표와 모순되던 버그가 있어 MA 문장에서 "저항/지지 우위" 표현을 제거한 흔적이 코드 주석에 남아 있다.

### 5-3. 반대 의견(동의하지 않는 지표)이 계산·표시되는 4갈래

| # | 무엇 | 계산 | 표시 |
|---|---|---|---|
| 1 | **컨플루언스** | `_allBias`(0 아닌 bias 전량) 중 종합방향 `_cdir`과 같은 부호 비율. `{score, agree, total}` | 판정 스트립 `컨플루언스 21/28 · 75%` |
| 2 | **방향 분포** | 지표별 `_nodeBias` 를 `>0.05 / |·|≤0.05 / <−0.05` 로 3분 | 판정 스트립 `방향 ▲18 · –4 · ▼9` + 레이더에서 좌우 막대로 시각화 |
| 3 | **반대 드리프트 되돌림** | `_opSum` (반대 방향 드리프트 절댓값 합)이 **예상 합의 절반 가중으로 항상 차감**. 캡(±0.05)에 가려지지 않도록 캡 이후 별도 차감 | 예측 경로 자체가 눌린다(수치 표기는 없음) |
| 4 | **3차 반대 시나리오선** | `counter[]` — 예상과 반대 방향의 **최근접 유의 지지/저항까지** 수렴. 거리는 데이터가 정함(비율 아님), 2.2σ 또는 ±20%로 캡 | 차트 3차선 + 끝점 배지 `3차·NN%` |

추가로: **모순 억제** — 종합 시그널과 반대 방향으로 크게 드리프트하면 `×0.25`. **끝점 확률 강등** — 1·2·3차 어느 선이든 끝점 캘리브레이션 확률이 50% 미만이면 회색 처리.

## 7. PC에 있는데 모바일에 없으면 아까운 것

> 근거와 함께. 우선순위 순.

1. **예측 시점별 표의 "예상 범위 바"** — 한 행 안에 `lo ── 현재가 ─── 예측가 ── hi` 를 한 트랙에 얹어, 불확실성의 크기를 **읽지 않고 보이게** 한다. 스코어카드 비교표상 앱은 "예측 구간 3카드"인데, 이 바 하나가 카드 3장보다 정보 밀도가 높고 세로 화면에 더 잘 맞는다.
2. **신뢰 레일 + 점묘 해체 + 끝점 확률 강등** — 예측선이 신뢰 지평을 지나면 **선이 점으로 해체되고**, 끝점 확률이 50% 미만이면 회색으로 내려간다. "이 선을 어디까지 믿어도 되는가"를 UI가 스스로 말하는 장치이고, 앱의 정직 표기 요구와 정확히 같은 문제를 이미 풀어 놓았다.
3. **`INDICATOR_INFO` 32종 × 3필드**(목적·정의·해석) — 순수 문자열 자산. 계산도 성능 부담도 없고, 잠긴 단계에서 "무엇이 빠졌는지를 이름으로 적는다"는 규율과 결합하면 **잠금 화면 자체가 학습 화면**이 된다.
4. **워치리스트 TF 신호등 3도트** — 목록 한 행에 일·주·월 판정을 3픽셀로 넣는다. 앱은 기본 단계에서 주·월이 잠기지만, **도트를 회색으로 두고 이름만 보여주는 것**만으로도 상위 단계의 존재를 정직하게 드러낸다.
5. **반대 시나리오의 근거 표기**(`counterBasis`) — PC조차 이 값을 화면에 안 쓴다(§1-2). "반대로 가면 어디까지" 를 **구조 레벨 / 변동성 1σ / 변동성 캡** 중 무엇으로 정했는지 한 단어로 붙이면, 3차선이 임의의 비율이 아님을 즉시 납득시킨다. **PC에도 없는 것이니 모바일이 먼저 가질 수 있다.**
6. **`prediction.levels`** — 예측이 참조한 기술적 레벨 전량(피보·구조·POC/VAH/VAL·볼린저·일목·VWAP)이 이미 정렬된 배열로 나온다. 지금은 예측선 꿈틀 계산에만 쓰이고 사용자에게 안 보인다. 차트 위 지지/저항 목록으로 그대로 쓸 수 있다.
7. **시뮬레이션 진행 로그** — 지표별 마지막 단계(=결론)를 강조 표시한 텍스트 로그가 그대로 **분석 리포트 본문**이 된다. 리빌이 끝난 뒤 남는 산출물이 있다는 점이 중요하다.
