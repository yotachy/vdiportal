# 리포트 화면군 ↔ 시안 시각 대조 감사 (2026-08-19)

프로젝트: **머니스쿱 앱 개편**. 대상: 리포트 화면군(P1a·P1b)만 — 온보딩 제외(이미 재작성 완료).
정보설계서(`docs/superpowers/specs/2026-08-18-moneyscoop-p1-design.md`)에 시각 규격이 없어(px·여백·타이포 0건),
각 태스크가 "기존 `build*` 패턴을 그대로 따르라"는 지시로 구현된 결과를 감사한다.

> 결론 선반영: **정보 구조·정직 표기 로직은 대체로 정교하다**(색 규칙 하나하나에 스펙 픽셀 샘플링
> 근거를 남긴 주석까지 있다). 그런데 그 정교한 정보를 담는 **그릇(컨테인먼트·반경·타이포 위계)**이
> 시안과 계 자체가 다르다 — 시안은 "카드 여러 개"로 말하고, 현재는 "헤어라인으로 구분한 리스트"로
> 말한다. 이 감사는 **읽기 전용**이다 — 코드를 고치지 않았다(`git status` 확인 완료).

## 1. 시안의 시각 언어 (수치)

| 항목 | 값 |
|---|---|
| 화면 가장자리 여백 | 좌우 **20px** (`margin:0 20px …`) — 이건 현재 구현(`.scr{padding:0 20px 40px}`)과 **이미 일치** |
| 블록 간 간격 | 카드 사이 **14px**(18a: `margin:0 20px 14px` 반복) |
| 카드 내부 패딩 | **18~22px**(카드 종류별 18/20/22px, 하나로 고정돼 있진 않지만 항상 이 대역) |
| **카드 반경** | **24~28px** 전역(콘텐츠 카드 24px·바이올렛/틴트 카드 26px·바텀시트 위 모서리 28px). 예외 없이 이 대역 — 시안 전체에서 11px 대역 반경은 한 번도 안 나온다 |
| 카드 배경(경계 처리) | **모든 정보 블록이 배경 틴트 + 반경을 가진 카드다.** 무채색 회색 카드(`rgba(238,241,247,.025~.09)`) 아니면 의미색 틴트 카드(골드 `rgba(232,180,99,.11)`·바이올렛 `rgba(184,146,245,.11)`) — **헤어라인 구분선으로 블록을 가르는 곳이 시안엔 없다** |
| 타이포 스케일(실측) | 헤드라인(판정어) **40~44px/800** → 시트 제목 **26px/800** → 화면 타이틀(종목명) **22~24px/800** → 소섹션 라벨 **12~15px/700** → 보조 캡션 **11~11.5px/400~500** — **가격은 캡션급(11.5px)**, 헤드라인 급이 아니다 |
| 밀도 | 18a(기본·무료)는 **딱 3블록**(판정+빗 / 차트 자리 / 내일 범위) + 해제 카드. 화면 하단 여백은 **의도된 빈 공간**("여기까지가 무료"의 증거로 명시) |
| 색 강조 위치 | 판정 방향색(bull `#4fb98a`/bear `#d96a6a`)은 헤드라인 글자·빗 중 "반대 칸" 1개에만. 화폐(스쿱)=골드, 행동(광고 CTA·바이올렛 카드)=`#b892f5` — 3색 규칙이 배경 틴트에도 그대로 적용됨 |
| 버튼 형태 | 주요 CTA는 **54px 높이 완전 필(반경 999px)**. 보조 버튼도 대개 필형 |

### 19a — 분석 진행 중계 / 8b — 해제 직후 전환

코드(`progress-analyze.js`+`style-reveal.css`)를 스펙과 직접 대조한 결과, **이 두 화면은 이 감사에서
가장 시안에 충실한 영역**이다: 이빨(tooth) 리빌 애니메이션, "방금 읽은 칸=흰색/이미 읽음=골드/기본

거의 1:1로 클래스명·주석에 대응한다(`style-reveal.css`가 8b·19a를 "생김새는 닮았지만 규칙이 반대라
클래스를 공유하지 않는다"고 명시할 정도로 스펙 의도를 정확히 읽었다). 다만:

- 스펙 19a는 지표별 방향 아이콘 색(상승=초록 계열/하락=핑크 계열)을 리스트 행에 명시하는데, 현재
  `an-row-*`엔 그 색 분기가 안 보인다(코드상 `an-row-text` 색이 `--ink-4` 고정) — 방향색이 최근 판독
  리스트에서 빠졌을 가능성. **실기기 스크린샷이 없어 확정은 못 함**(이 감사가 열람 전용이라 새로
  찍지 않았다) — 다음 관문에서 `mobile/tools/shots.sh`로 스크린샷을 뜬 뒤 재확인 필요.

### 20a — 판독문 32개

레이아웃 얼개(뒤로가기+타이틀+필터 세그 4개+카드 리스트)는 스펙과 구조적으로 동일. 코드 주석
(`style-report.css` L232-234)이 "판독은 행으로 정렬한다 — 예전엔 여섯 줄짜리 다색 칩 덩어리였는데
시안엔 그런 요소가 없어 이름/값 두 칸으로 바꿨다"고 스스로 스펙 대조 이력을 남겨 뒀다 — **이 화면은
과거 한 차례 스펙 정합 작업을 거친 흔적**이 뚜렷하다. 남은 차이는 카드 반경(스펙은 카드 자체가 없고
필터 세그만 `border-radius:10px`인 얕은 화면이라 반경 이슈가 거의 없음)과 지표 카드 배경(스펙엔 각
지표 항목에도 옅은 카드 배경이 있는데 현재는 `.rp-lg-chip`이 헤어라인 구분 리스트).

### 18c·10a — 전문분석·가중치 조절판

시안 10a는 **전용 편집 화면**(뒤로가기 있는 풀스크린, 기준 성향 세그 4개+지표별 슬라이더 리스트,
슬라이더 트랙 150px 폭 근거까지 주석에 남아 있음)인데, 현재 구현은 `.rp-weights`(리포트 화면 안에
접힌 12px 반경 카드 하나로 삽입, `style-reveal.css` L67-70)로 되어 있어 **구조 자체가 다르다** —
스펙은 별도 화면(뒤로가기 이동), 현재는 리포트 내부 인라인 패널. `shots/`에 이 상태 캡처가 없어
현재 실제 UI 볼륨은 코드로만 확인했다(`.rp-weights-edit`가 `min-height:44px`인 단일 입력처럼 보여
스펙의 다중 슬라이더 리스트만큼 풍부한지 불확실).

**시각적** (배치는 비슷한데 여백·타이포·밀도·색이 다름) — **이번 감사의 절대다수가 여기**

## 4. 상위 5개 수정 항목 (임팩트 순)

1. **카드 컨테인먼트 시스템 도입** — `style-report.css`의 섹션 wrapper 클래스들(`.rp-verdict-wrap`·

   var(--hairline)` 패턴을 `border-radius:24px` + 배경 틴트로 교체. **이거 하나가 "시안 느낌"의

2. **타이포 위계 뒤집기** — `.rp-head-sym`을 `--fs-section`(17px)에서 `--fs-title`(22px)급으로,

   단일 히어로 원칙 복원. 파일: `style-report.css` L10, L17.
3. **해제 CTA 골드화** — `.rp-unlock`(`style-report.css` L283)의 반경 12→24, 배경을 골드 틴트로,
   버튼을 54px 필형으로. 단, 현재 바이올렛 처리는 "행동=바이올렛"이라는 **문서화된 의도적 3색

## 5. 정보 구조 유지한 채 표현만 바꿀 수 있는가

**대부분 가능.** 1·2·5번은 **CSS 토큰/클래스 값 교체만으로** 끝난다 — 정보 순서·문구·데이터는
그대로 두고 반경·배경·폰트 크기 변수만 바꾸면 된다. 3·4번도 CSS 위주이나, 시안처럼 "판정+부제+
지표빗"을 **한 카드**로 묶으려면(6a/18a) report.js에서 형제로 append 중인 `buildVerdict()`와
`buildComb()`의 반환 요소를 **공통 wrapper 하나로 감싸는** 작은 DOM 구조 변경이 필요하다(정보
자체의 순서·계층은 안 바뀜 — 같은 요소들을 담는 그릇만 하나로 합친다).

**구조까지 손대야 하는 곳은 둘**: (a) 10a 전문분석 조절판을 스펙처럼 독립 화면으로 분리하려면
라우팅·뒤로가기 흐름이 새로 필요하고, (b) 14a 검색창/필터칩을 스펙대로 없애는 것은 기능 제거라
정보구조 변경이다(이건 "표현" 문제가 아니라 "이 기능을 지금 뺄 것인가"라는 제품 판단).

## 6. `report.js` 1822줄 · `style-report.css` 328줄 — 재작업을 방해하는가

**막지 않는다.** 근거:

- report.js는 섹션별 `build*()` 함수(`buildVerdict`·`buildComb`·`buildForecast`… )로 이미 잘
  모듈화돼 있다 — 각 함수가 정확히 한 wrapper `div`를 만들어 반환하고 호출부가 순서대로
  append하는 구조다. 위 §5의 "형제를 wrapper로 묶기" 같은 작업은 **해당 함수 몇 개만** 건드리면
  되고, 1822줄 전체를 이해해야 하는 작업이 아니다.
- 시각 값(반경·배경·폰트크기·색)이 **JS 리터럴이 아니라 전부 CSS 클래스/토큰에** 있다(report.js를
  grep해도 `border-radius` 리터럴이 0건 — 스타일은 항상 `style-report.css`가 담당). 그래서 "시각을
  바꾼다"는 작업의 실제 표면적은 328줄짜리 CSS 파일 쪽이 훨씬 크고, report.js는 §5에서 언급한
  극소수 wrapper 추가에만 노출된다.
- CSS 328줄도 섹션별 블록(`.rp-*` 접두사로 이미 네임스페이스됨, 주석으로 각 블록이 어느 스펙
  프레임 담당인지 표시돼 있음 — 예: "해제 카드(시안 8b)")이 명확해 쪼개지 않아도 국소 수정이
  가능하다. 다만 §4의 1번(카드 시스템)처럼 **모든 섹션에 걸친 일괄 규칙**을 넣을 거라면, 새
  유틸리티 클래스(`.rp-card`류) 하나를 만들어 각 섹션 wrapper에 얹는 편이 328줄 전체를 개별
  수정하는 것보다 안전하다 — 이건 "쪼개야 한다"가 아니라 "공통 클래스를 하나 신설하라"는 뜻이다.

**결론**: 파일을 분할할 필요는 없다. 정보 구조를 그대로 둔 시각 재작업은 CSS 우선 + 소수의 wrapper
추가로 충분한 규모다.
